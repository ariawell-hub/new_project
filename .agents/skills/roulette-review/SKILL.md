# 랜덤 식단 룰렛 코드 리뷰

목표는 사용자가 실제로 겪을 버그를 커밋 전에 잡는 것이다. 스타일과 사소한 취향은 린터(ESLint, html-validate)에 맡기고, 리뷰는 "어떤 조작을 하면 무엇이 잘못되는가"에 집중한다.
리뷰만 한다. 사용자가 고쳐 달라고 하기 전에는 파일을 수정하지 않는다.

## 1. 리뷰 범위 정하기

요청에 파일, 커밋, 브랜치가 지정되어 있으면 그 범위만 본다. 없으면 아래 순서로 처음 비어 있지 않은 것을 범위로 삼는다.

1. `git diff --cached` (스테이지된 변경 — 곧 커밋될 내용)
2. `git diff` (작업 중인 변경)
3. `git diff HEAD~1` (마지막 커밋)
4. 커밋이 하나도 없으면 `git status --short`에 보이는 파일 전체

바뀐 줄만 읽지 말고, 바뀐 함수를 부르는 쪽과 바뀐 함수가 부르는 쪽까지 읽는다. 버그는 대개 경계에서 생긴다.

## 2. 자동 검사 먼저

`npm run check`(린트 → 빌드 → 테스트)를 실행한다. 실패하면 그것이 최우선 지적 사항이다. 실패 원인을 요약하고 어느 파일 몇 번째 줄인지 적는다.
린트가 이미 잡는 문제(쓰지 않는 변수, HTML 문법 등)를 리뷰에서 다시 지적하지 않는다.

## 3. 알아야 할 구조

| 파일 | 역할 |
|---|---|
| `roulette.js` | 순수 로직. 브라우저에서는 `window.Roulette`, 테스트에서는 `require`. DOM을 건드리지 않는다. |
| `index.html` | 화면과 이벤트 처리. 로직은 `R.함수명`으로 호출한다. |
| `scripts/build.mjs` | `<script src="roulette.js">`를 내용으로 바꿔 `dist/index.html` 한 파일을 만든다. |
| `test/*.test.js` | `node:test` 단위 테스트. `build.test.js`는 index.html이 쓰는 `R.*` 이름이 실제로 있는지도 확인한다. |
| `.githooks/pre-commit`, `.Codex/hooks/pre-commit-check.mjs` | 커밋 전에 `npm run check`를 돌리는 훅. |

상태는 localStorage `lunchRoulette.v1`에 `{ menus, history, settings }`로 저장되고, 읽을 때 `R.normalizeState`를 거친다.

## 4. 체크리스트

각 항목은 이 프로젝트에서 실제로 깨지기 쉬운 곳이다. 변경과 관련된 항목만 깊게 본다.

1. **룰렛 결과와 포인터 일치.** 당첨 칸을 먼저 고르고 `R.spinRotation`으로 회전량을 맞춘다. 화면의 회전 각도를 읽어서 결과를 정하거나, 도는 중에 `wheelItems`를 바꾸면(`spinning`/`pendingRefresh` 가드를 우회하면) 포인터가 가리키는 칸과 결과 카드가 달라진다. 이 프로젝트에서 가장 눈에 띄는 버그다.
2. **저장 데이터 호환.** 사용자의 메뉴와 기록은 브라우저에 남아 있다. 저장 구조를 바꾸면 `normalizeState`가 예전 형식을 받아도 메뉴나 기록을 통째로 버리지 않는지 본다. 새 필드에는 기본값을 주고, 키를 바꾸면 옮겨 담는 코드가 있어야 한다. localStorage 읽기·쓰기는 시크릿 창에서 예외가 나므로 try/catch 안에 있어야 한다.
3. **사용자 입력과 innerHTML.** 메뉴 이름은 사용자가 입력한다. `innerHTML` 템플릿에 들어가면 반드시 `esc()`(= `R.escapeHtml`)를 거쳐야 하고, 가능하면 `textContent`를 쓴다. 이스케이프가 빠지면 메뉴 이름 하나로 화면이 깨지거나 스크립트가 실행된다.
4. **날짜는 로컬 달력 기준.** 날짜는 `R.fmtDate(new Date())`로 만든 `YYYY-MM-DD`와 `R.dayDiff`로 비교한다. `toISOString()`은 UTC라서 한국 시간 오전 9시 전에는 전날 날짜가 나오고, `Date.now()` 차이를 24시간으로 나누면 점심시간 전후로 "최근 N일" 판정이 바뀐다.
5. **오프라인 단일 파일 유지.** 더블클릭(file://)으로 열고, 빌드 결과 한 파일만 공유해도 동작해야 한다. 외부 CDN이나 `fetch`를 추가하면 오프라인에서 깨진다. `<script type="module">`은 file://에서 막힌다. `roulette.js` 안에 `</script` 문자열이 들어가면 빌드가 실패한다.
6. **로직의 위치와 테스트.** 계산 로직은 `roulette.js`에 두고 테스트를 붙인다. `index.html` 안에 계산을 새로 짜 넣으면 테스트가 닿지 않는다. 새 `R.*` 함수는 `roulette.js` 맨 아래 반환 객체에 들어 있어야 한다.
7. **예외 상황.** 후보 0개, 후보 1개, 카테고리를 모두 끔, 빈 이름이나 중복 이름 추가, 기록 지우기 직후, 시크릿 창. 변경이 이 경로를 건드리면 실제로 따라가 본다.
8. **모바일과 접근성.** 375px 폭에서 가로 스크롤이 생기지 않아야 한다. 회전하거나 크기가 변하는 요소는 `.wheel-clip`처럼 `overflow: hidden`인 틀 안에 둔다. 버튼에는 `type`, 아이콘만 있는 요소에는 `aria-label`을 붙이고, 애니메이션은 `prefers-reduced-motion`을 존중한다. 색은 `:root` CSS 변수를 써야 다크모드에서 깨지지 않는다(원판의 파스텔 칸은 의도적으로 고정색이다).
9. **검사 장치 자체.** `package.json` scripts, `.githooks/`, `.Codex/settings.json`, `.Codex/hooks/`를 바꾸면 검사가 조용히 꺼지거나 항상 통과하게 되지 않았는지 본다.

## 5. 지적하기 전에 확인하기

후보 문제마다 구체적인 시나리오로 확인한다. 코드 경로를 따라가고, 로직 문제라면 `node -e "const R=require('./roulette.js'); ..."`로 직접 재현해 본다.
확인되지 않은 의심은 버리거나 "확인 필요"로 낮춘다. 추측으로 채운 리뷰는 진짜 문제까지 묻히게 만든다.

## 6. 보고 형식

아래 형식을 그대로 쓴다. 심각도 순으로, 확인된 것만 최대 10개까지 적는다.

```markdown
## 리뷰 결과: <범위 — 예: 스테이지된 변경 3개 파일>

자동 검사: `npm run check` 통과 | 실패 (<한 줄 요약>)

### 🔴 반드시 고칠 것
1. `roulette.js:42` — <한 줄 요약>
   - 상황: <어떤 입력이나 조작을 하면> → <무엇이 잘못되는지>
   - 근거: <어떻게 확인했는지 — 따라간 코드 경로, 재현 명령과 결과>
   - 제안: <고치는 방법. 코드는 짧게>

### 🟡 고치면 좋은 것
(같은 형식)

### 💬 참고
(선택. 버그는 아니지만 알아두면 좋은 점 1~3개)
```

- 🔴: 사용자가 겪는 오작동, 데이터 손실, 보안 문제, 검사 실패
- 🟡: 특정 조건에서만 생기는 문제, 테스트 누락, 유지보수를 어렵게 만드는 구조

문제가 없으면 "발견된 문제 없음"이라고 쓰고, 확인한 범위와 실행한 검사를 적는다. 문제가 없다는 결론도 근거가 있어야 믿을 수 있다.
